# The new curve (#356) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A short check-in has things worth buying all run. Machines cost about ×1.15 per unit and workers about ×1.08, and each deeper band takes more stones per stretch of depth, so income grows across the run and every tier stays worth a look.

**Architecture:**

- Depth stays in run-1 units everywhere (relics, layers, materials, reveals, saves).
- A per-band stone scale `s_b` lives in the leaf module `src/scale.ts`, beside the kid-run stretch `k`. A stone dug in band _b_ digs 1/(k·s_b) of a stone of depth.
- Three pure functions convert between depth and pocket stones: `shownStones`, `stonesLeft` and the new `depthAfterStones`. `digStones` and every screen go through them, so live, away, taps, lock cards and the legend cannot drift.
- Prices do not scale with s.
- Cost curves change in `src/tiers.ts`. The lab then tunes `s` and any first price against the guardrails.

**Tech Stack:** TypeScript, Vitest (happy-dom for screens), the strategy lab (`npm run lab`, `npm run lab:generations`), the Firestore emulator rules test (`npm run gate -- full`, step `rules`).

**Spec:** `docs/economy-overhaul.md`, sections A, B and F, and its "Decided" section. Evidence: `docs/balance-review.md`. Lab measures: `docs/DESIGN.md`, "Check-in pacing".

## Global Constraints

- Machines (cart, drill, borer, Great Machine) grow about ×1.15 per unit. Workers and kids grow about ×1.08 (D1). The exact values stay in 1.10–1.15 for machines and 1.06–1.10 for workers, picked by the lab in Task 5.
- Band scales start at s = 1 / 3 / 9 / 27 for the Topsoil, Granite, Crystal Caves and Deep Heart (D2). The Topsoil stays 1. The lab settles the rest, by feel.
- **The run length is not a limit** (Decided, 7 Nov 2026). Run 1's finish day is reported, not graded. The kid-run rule (each run finishes later than the one before, with every machine bought) stays strict.
- The new numbers apply to the run in progress, with no save field and no migration (Decided).
- Prices never scale with s. They keep scaling with the kid-run stretch k, as today.
- Numbers rule: real prices and gains, never payback or "best". Discoveries stay vague. No "?" in player text.
- The phone layout never scrolls. Visual check at 390×844, 360×640 and 360×560.
- `src/scale.ts` stays a leaf module (no imports from `layers.ts` or `mountain.ts`), because `scripts/check-cycles.mjs` fails on a cycle.
- No lab bound in `src/lab/targets.ts` changes. The four check-in rows stay report-only in this sliver (they turn strict in #357).
- Commit messages: a plain sentence ending in `(#356)`.

## Review Focus

1. **One away haul crossing two or more band boundaries** (from 9M to 50M of depth, say). The depth, the materials per band and the stones left must all be exact. Task 2 pins it.
2. **The last stones of the mountain in a deep band.** `remaining` must reach exactly 0, not a float crumb, and taps and away pay stop there. Task 2 pins it.
3. **An existing save mid-Crystal loads.** Stones left reads larger, prices for owned counts read lower, and nothing is NaN or negative. Task 3 pins it with an old fixture through `parseSaveValue`.
4. **A kid run with k ≠ 1 composes with s.** `shownStones(m, MOUNTAIN_STONES)` = k × Σ band depth × s_b. Prices are × k only. Task 1 pins it.
5. **The saved `remaining` is rounded up to a whole depth stone** (`persist.ts:99`). In a deep band one depth stone is k·s stones, so a reload may give back up to that many stones of depth, but never more mined than was dug. Task 2 pins it.

### Task 1: Band scales and depth↔stones conversion in `src/scale.ts`

**Files:**

- Modify: `src/scale.ts`, `src/layers.ts` (the `LAYERS[*].from` literals read `BAND_STARTS`)
- Test: `src/scale.test.ts`

**Interfaces:**

- Produces:
  - `BAND_STARTS: readonly [0, 10_000_000, 45_000_000, 120_000_000]`, depth where each band begins. `LAYERS[i].from === BAND_STARTS[i]`.
  - `BAND_SCALE: readonly [1, 3, 9, 27]`, stones per depth stone in each band at k = 1.
  - `bandScale(band: 0 | 1 | 2 | 3): number` = `BAND_SCALE[band] * factor(\`band.${band + 1}.scale\`)` (the lab's knob; 1 in play).
  - `shownStones(mountain: { stretch?: number }, depth: number): number`: pocket stones to dig from the surface to `depth`, = k × Σ_b overlap([0, depth], band b) × bandScale(b). Same signature as today.
  - `stonesLeft(mountain: Sized): number` = `shownStones(m, MOUNTAIN_STONES) − shownStones(m, minedOut(m))`. Same signature.
  - `depthAfterStones(mountain: Sized, stones: number): number`: the mined-out depth after digging `stones` more pocket stones from `minedOut(mountain)`, walking band by band, capped at `MOUNTAIN_STONES`.

- [ ] **Step 1: Write failing tests** in `src/scale.test.ts`, in a new `describe("band scales (#356)")`. Expected values are computed from the exported constants, not hard-coded, so Task 5 can retune them:
  - `shownStones(createMountain(), 10_000_000)` equals `10_000_000 * BAND_SCALE[0]`.
  - `shownStones(createMountain(), 45_000_000)` equals `10_000_000 * BAND_SCALE[0] + 35_000_000 * BAND_SCALE[1]`.
  - `shownStones(createMountain(), MOUNTAIN_STONES)` equals the four-band sum.
  - With `{ ...createMountain(), stretch: 1.75 }` the same three values are × 1.75 (Review Focus 4).
  - `stonesLeft` of a fresh mountain equals `shownStones(fresh, MOUNTAIN_STONES)`. `stonesLeft` at 9M mined equals the full sum minus `9_000_000 * BAND_SCALE[0]`.
  - `depthAfterStones(minedMountain(9_000_000), 1_000_000 * BAND_SCALE[0] + 3_000_000 * BAND_SCALE[1])` is `13_000_000`: the first million at the Topsoil scale, the next 3M of depth at the Granite scale.
  - `depthAfterStones(minedMountain(9_000_000), stonesLeft(minedMountain(9_000_000)) * 2)` is `MOUNTAIN_STONES`.
  - `withFactors({ "band.2.scale": 2 }, …)` doubles the Granite part of `shownStones(fresh, 45_000_000)`.
  - The existing `kid-run stretch` tests that call `shownStones` and `stonesLeft` keep passing. Update only expectations that assumed a flat k × depth, and compute them from `BAND_SCALE`.
